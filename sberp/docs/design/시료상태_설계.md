# 시료상태 설계

- 근거: `창고_시료관리_업무규칙_정의서_v2` (2026-09-29) · `창고_독자번호_v12.html` (2026-10-15)
- 방식: **저장** — 상태를 칼럼에 들고 있고, 바뀔 때마다 이력을 남긴다 (2026-10-16 결정)

> **[번호 전환]** 시료번호 체계가 바뀌었다(`S26-00001`, 2026-10-16 확정). 새 시료는 `IM_SUB_TB` 에 `IM_ID = 'S26'`(해) · `IM_SUB_SEQ` = 그해 순번으로 넣고 `IM_TB` 는 거치지 않는 방향이다(2026-10-19) — `시료번호_전환.md`.
> 그래서 이 문서의 칼럼 · 이력 키(`IM_ID` + `IM_SUB_SEQ`)는 대부분 그대로 쓴다. 바뀌는 곳만 표시했다.
> 이 문서에서 영향받는 곳마다 `[번호 전환]` 을 달았다. 시료 기획이 끝나면 함께 고친다.

## 0. 지금 어디까지 와 있나

**아직 한 줄도 구현하지 않았다.** 이 문서는 설계안이고, 창고를 먼저 끝낸 뒤 시작한다(2026-10-16).

현재 코드에 있는 것과 없는 것.

| | 상태 |
|---|---|
| `IM_SUB_TB.CURRENT_ZONE_SEQ` | 있다. 위치 스캔(`/sam/loc/scan.do`)이 채운다 |
| `IM_SUB_LOC_TB` | 있다. 구역 이동 이력 |
| `ZONE_TB.USE_CODE` | 있다. 일반 · 인수요청 · 장기 |
| `IM_SUB_TB.PROC_STATE` | 있지만 **쓰는 코드가 없다.** 옛 설계 잔재 |
| 시료상태 칼럼 · 이력 테이블 | **없다** |
| 용도 변경 시 시료 상태 일괄 변경 | **없다** (`TC_str_zone_update.md` ZU2) |
| 시험부 점유(`IM_SUB_OCCUPY_TB` 등) | 서비스 · 컨트롤러는 지워졌고 테이블 · 칼럼만 남아 있다 |

> **[번호 전환]** 위 표의 `CURRENT_ZONE_SEQ` · `IM_SUB_LOC_TB` 는 그대로 쓴다. 위치 스캔은 새 번호를 찾는 조회만 더한다(`시료번호_전환.md` 7장).
> `IM_SUB_LOC_TB` 는 원래 있던 빈 테이블(옛 「시료위치」)을 `SAM_ZONE_LOC.sql` 이 새 구조로 다시 만든 것이고, `IM_SUB_OCCUPY_TB` 는 창고 작업 때 새로 만든 것이다.

착수 순서는 **9장의 ①(프로젝트 완료일 확정) → 7장 DDL → 5장 용도 변경 일괄 처리 → 폰 API** 다.

## 1. 상태값

시료 하나는 한 값만 가진다. 공통코드 그룹 `IS` 로 등록한다.

| 코드 | 이름 | 뜻 |
|---|---|---|
| `01` | 보유 | 회사 안, 창고 밖. 누군가 들고 있다 |
| `02` | 보관 | 일반 구역 안 |
| `03` | 보관(인수요청) | 인수요청 구역 안. 고객지원부가 가져갈 시료 |
| `04` | 보관(장기) | 장기 구역 안. 고객 요청으로 오래 둔다 |
| `05` | 외출 | 회사 밖. 돌아올 시료 |
| `06` | 반출 | 밖으로 나가서 끝났다 |
| `07` | 폐기 | 없어졌다 |

`02`·`03`·`04` 를 「보관 3종」이라 부른다. 셋 다 구역 안에 있고, **구역의 용도가 곧 상태**다.

| 구역 용도(`ZONE_TB.USE_CODE`) | 시료상태 |
|---|---|
| `01` 일반 | `02` 보관 |
| `02` 인수요청 | `03` 보관(인수요청) |
| `03` 장기 | `04` 보관(장기) |

현장시험 · 미반입 시료는 상태를 갖지 않는다. 시료 행은 PC 반입 등록 때 생기고, 이 구분은 신청서 쪽 공통코드 `CI` 로 본다.

> **[번호 전환]** 시료 행은 **시료 QR 출력** 때 생긴다(출력 = 반입). 신청서 없이도 생기므로 신청서 쪽 `CI` 로 가를 일이 없다 — QR 을 뽑지 않은 물건은 애초에 시료 행이 없다.

## 2. 어디에 저장하나

`IM_SUB_TB` 에 칼럼을 더한다.

> **[번호 전환]** 칼럼은 그대로 `IM_SUB_TB` 에 더한다. 상태를 갖는 것은 **새 줄(`IM_ID LIKE 'S%'`)뿐**이고 옛 줄은 `NULL` 로 둔다.

| 칼럼 | 타입 | 뜻 |
|---|---|---|
| `SST_CODE` | varchar(2) | 현재 시료상태 |
| `SST_DT` | datetime | **이 상태가 된 시각** |
| `SST_MEM_ID` | varchar(20) | 이 상태로 바꾼 사람 |
| `PICK_MEMO` | varchar(500) | 인수요청 메모. 구역에 못 들어가는 큰 시료의 실제 위치 |
| `OUT_DAYS` | int | 끝난 외출 기간의 합(일). 반출대기에서 뺀다 |

`CURRENT_ZONE_SEQ` 는 이미 있다. 보관 3종일 때만 값이 있고, 꺼내기 · 외출 · 반출 · 폐기 때 `NULL` 로 지운다.

### `SST_DT` 를 따로 두는 이유

업무규칙 87번이 짚은 문제다.

> 인수요청 경과를 보관 기록(`IM_SUB_LOC_TB` 최신 행) 시각으로만 잡으면, 용도 변경으로 인수요청이 된 시료는 틀리게 나온다.

인수요청 경과는 「인수요청이 된 때」부터 센다(규칙 80). 그 시점은 **구역 QR 스캔** 또는 **구역 용도 변경** 둘 중 하나인데, 용도 변경은 구역 이동이 아니라서 `IM_SUB_LOC_TB` 에 줄이 생기지 않는다. 상태가 바뀐 시각을 따로 들고 있어야 두 경우가 같이 맞는다.

### `SST_MEM_ID` 를 비정규화하는 이유

「최종 처리」(마지막으로 상태를 바꾼 사람 · 날짜)는 시료 리스트의 모든 행에 나온다(규칙 118). 이력 테이블에서 행마다 최신 줄을 찾으면 목록 조회에 상관 서브쿼리가 붙는다. 값은 이력과 같지만 읽기 비용 때문에 칼럼으로 둔다.

## 3. 이력 — `IM_SUB_HIS_TB` 신설

| 칼럼 | 타입 | 뜻 |
|---|---|---|
| `IM_SUB_HIS_SEQ` | int PK | |
| `IM_ID` · `IM_SUB_SEQ` | | 시료 — **[번호 전환]** 새 줄만 들어온다. 키는 그대로 |
| `ACT_CODE` | varchar(2) | 동작. 공통코드 `IA` |
| `SST_CODE` | varchar(2) NULL | 이 동작 **뒤**의 상태. 상태가 안 바뀌는 동작이면 `NULL` |
| `ZONE_SEQ` | int NULL | 관련 구역 |
| `DETAIL` | varchar(500) | 상세. 구역명 · 외출지 · 용도 변경 전후 등 |
| `PHOTO_CNT` | int | 사진 장수 |
| `PC_YN` | char(1) | `Y` PC 에서 한 일 · `N` 폰 스캔 |
| `INS_MEM_ID` · `INS_DT` · `STATE` | | |

### 동작 코드 (`IA`)

| 코드 | 동작 | 상태 바뀜 | 어디서 |
|---|---|---|---|
| `01` | 반입등록 | → 보유 | PC — **[번호 전환]** 시료 QR 출력 |
| `02` | 보관 | → 보관 3종 | 폰 |
| `03` | 꺼내기 | → 보유 | 폰 |
| `04` | 외출 | → 외출 | 폰 |
| `05` | 복귀 | → 보유 | 폰 |
| `06` | 반출 | → 반출 | 폰 |
| `07` | 폐기 | → 폐기 | 폰 |
| `08` | 확인 | 안 바뀜 | 폰 |
| `09` | 사진 | 안 바뀜 | 폰 |
| `10` | 용도변경 | → 보관 3종 | PC |
| `11` | 시험상태변경 | 안 바뀜 | PC |

세 가지 화면 값이 모두 이 한 테이블에서 나온다.

- **상태 변경 보기** = `SST_CODE IS NOT NULL` 인 줄 (기본 보기)
- **전체 보기** = 모든 줄
- **마지막 스캔** = `PC_YN='N'` 중 최신 — PC 에서 한 일은 스캔이 아니다(규칙 127)

같은 사람이 같은 날 여러 번 찍은 `08 확인` 은 조회할 때 한 줄로 합친다(「찍기만 함 · 3번」). 저장은 줄마다 한다.

## 4. 상태 전이

| 지금 | 동작 | 다음 | 부수 처리 |
|---|---|---|---|
| — | 반입등록(PC) | 보유 | 시료 행 생성 |
| 보유 | 보관(구역 QR) | 구역 용도에 맞는 보관 3종 | `CURRENT_ZONE_SEQ` 설정 |
| 보관 3종 | 꺼내기 | 보유 | `CURRENT_ZONE_SEQ` · `PICK_MEMO` 지움 |
| 보관 3종 | 다른 구역 QR | 새 구역 용도에 맞는 보관 3종 | 이전 구역에서 자동으로 빠짐 |
| 보관 3종 | **용도변경(PC)** | 새 용도에 맞는 보관 3종 | 인수요청이 아니게 되면 `PICK_MEMO` 지움 |
| 보유 · 보관 3종 | 외출 | 외출 | `CURRENT_ZONE_SEQ` 지움, 외출지·메모를 이력에 |
| 외출 | 복귀 | 보유 | `OUT_DAYS += 오늘 − SST_DT` |
| 보유 · 보관 3종 | 반출 | 반출 | `CURRENT_ZONE_SEQ` 지움 |
| 보유 · 보관 3종 | 폐기 | 폐기 | `CURRENT_ZONE_SEQ` 지움 |
| 어디서나 | 확인 · 사진 | 그대로 | 이력만 |

> **[번호 전환]** 「반입등록(PC)」은 **시료 QR 출력**이다. 신청서 연결 · QR 다시 출력도 이력에 남길지 동작 코드를 정해야 한다.

꺼내기 사유는 묻지 않는다. 누가 꺼냈는지만 남긴다(규칙 18).
반출 · 폐기는 꺼내기 없이 바로 할 수 있다(규칙 11).

## 5. 구역 용도 변경 — 일괄 처리

`/cnf/str/zone/update.do` 로 `useCode` 가 바뀔 때 한 트랜잭션 안에서 처리한다.

```
1. 구역 용도 UPDATE
2. 그 구역의 보관 3종 시료를 모두 찾는다
     WHERE CURRENT_ZONE_SEQ = ? AND SST_CODE IN ('02','03','04')
       AND STATE != 'D' AND IFNULL(CARRY_OUT_CODE,'') = ''
3. UPDATE IM_SUB_TB
     SET SST_CODE = 새 용도에 맞는 상태,
         SST_DT = NOW(), SST_MEM_ID = 로그인,
         PICK_MEMO = (새 상태가 03 이 아니면 NULL)
4. 시료마다 이력 1줄
     ACT_CODE='10', SST_CODE=새 상태, PC_YN='Y',
     DETAIL='1창고 가-04 · 일반 → 인수요청'
5. 응답에 바뀐 건수를 담는다
```

> **[번호 전환]** 테이블 · 키는 그대로다. 옛 시료는 구역에 들어가지 않으므로 2 의 대상은 새 줄뿐이다.

확인창(규칙 64)은 바꾸기 **전에** 건수를 보여줘야 하므로, 프런트가 미리 물을 수단이 필요하다. 창고 상세의 `zones[].itemCnt` 가 이미 그 구역의 보관 건수라 그대로 쓸 수 있다. 별도 API 는 두지 않는다.

이미 같은 용도면 아무 일도 하지 않는다(현재 구현도 그렇다).

## 7. DDL 초안

> **[번호 전환]** `ALTER` · `CREATE` 는 그대로 쓴다. 새 번호용 칼럼 · 연결 · 채번 테이블은 `시료번호_전환.md` 4장.
> 맨 아래 **초기값 UPDATE 는 필요 없어진다.** 옛 시료는 상태를 갖지 않고, 새 QR 을 붙이는 순간 새 시료로 보유에서 시작한다.

```sql
ALTER TABLE `IM_SUB_TB`
  ADD COLUMN `SST_CODE`   varchar(2)   DEFAULT NULL COMMENT '시료상태(공통코드:IS)',
  ADD COLUMN `SST_DT`     datetime     DEFAULT NULL COMMENT '그 상태가 된 시각',
  ADD COLUMN `SST_MEM_ID` varchar(20)  DEFAULT NULL COMMENT '상태를 바꾼 사람',
  ADD COLUMN `PICK_MEMO`  varchar(500) DEFAULT NULL COMMENT '인수요청 메모',
  ADD COLUMN `OUT_DAYS`   int NOT NULL DEFAULT 0    COMMENT '끝난 외출 기간 합(일)';

ALTER TABLE `IM_SUB_TB` ADD KEY `IDX_IM_SUB_SST` (`SST_CODE`, `SST_DT`);

CREATE TABLE `IM_SUB_HIS_TB` (
  `IM_SUB_HIS_SEQ` int NOT NULL AUTO_INCREMENT,
  `IM_ID`      varchar(20)  NOT NULL,
  `IM_SUB_SEQ` int          NOT NULL,
  `ACT_CODE`   varchar(2)   NOT NULL     COMMENT '동작(공통코드:IA)',
  `SST_CODE`   varchar(2)   DEFAULT NULL COMMENT '동작 뒤의 시료상태. 안 바뀌면 NULL',
  `ZONE_SEQ`   int          DEFAULT NULL,
  `DETAIL`     varchar(500) DEFAULT NULL,
  `PHOTO_CNT`  int NOT NULL DEFAULT 0,
  `PC_YN`      char(1)  NOT NULL DEFAULT 'N' COMMENT 'Y PC · N 폰 스캔',
  `INS_MEM_ID` varchar(20) DEFAULT NULL,
  `INS_DT`     datetime DEFAULT CURRENT_TIMESTAMP,
  `STATE`      varchar(1) NOT NULL DEFAULT 'I',
  PRIMARY KEY (`IM_SUB_HIS_SEQ`),
  KEY `IDX_HIS_ITEM` (`IM_ID`,`IM_SUB_SEQ`,`IM_SUB_HIS_SEQ`),
  KEY `IDX_HIS_SCAN` (`IM_ID`,`IM_SUB_SEQ`,`PC_YN`,`IM_SUB_HIS_SEQ`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8 COMMENT='시료상태 이력';
```

초기값 — 기존 시료는 반입 등록이 이미 끝나 있으므로 보유로 시작한다. 반출된 건은 반출로 둔다.

```sql
UPDATE `IM_SUB_TB`
   SET `SST_CODE` = IF(IFNULL(`CARRY_OUT_CODE`,'') = '', '01', '06'),
       `SST_DT`   = IFNULL(`CARRY_IN_DATE`, `INS_DT`)
 WHERE `SST_CODE` IS NULL AND `STATE` != 'D';
```

도입 첫날에는 스캔 기록이 없어 전부 「스캔 없음」으로 나온다(규칙 128). 의도된 모습이다.

| `IM_SUB_OCCUPY_TB` | 위와 같음. 서비스 · 컨트롤러 코드는 이미 지워졌고 테이블만 남아 있다 |
| `SamProcStateSupport.procName()` | `PROC_STATE` 전용 |

> **[번호 전환]** 그대로 걷어낸다. 옛 시료 리스트 조회(`selectList`)가 `PROC_STATE` 를 읽고 있으니 함께 뺀다.

## 9. 확정이 필요한 것

### ① 「프로젝트 완료일」이 어느 칼럼인가

반출대기의 기준점인데 아직 정해지지 않았다. 후보는 셋이다.

- `JOB_TB.STATE_CODE`(공통코드 `CP`) 가 완료일 때의 `STATE_UDT_DT`
- `TEST_TB.REPORT_DT` — 성적서 발급일
- `SBK_TB.EST_CMP_DT` — **예상** 완료일이라 실적이 아니다

업무규칙 121번이 「가장 마지막 프로젝트 완료일」이라고 쓴 것은 시료 하나가 여러 신청서에 걸릴 수 있다는 전제다. 지금 백엔드는 시료 ↔ 신청서가 1:1(`IM_TB.SBK_ID`)이라 「가장 마지막」이 성립하지 않는다. 다대다 연결을 만들 계획인지도 같이 정해야 한다.

> **[번호 전환]** 다대다는 **확정**이다. 새 시료는 연결 테이블(가칭 `IM_SUB_LINK_TB`)로 여러 신청서에 이어진다. 남은 것은 완료일 칼럼 선택뿐이고, 「가장 마지막」은 연결된 신청서 전부의 완료일 중 최댓값이다. 목업은 연결된 신청서 중 하나라도 끝나지 않은 시험이 있으면 반출대기를 세지 않는다.

### ② 공통코드 그룹 두 개

`IS`(시료상태) · `IA`(동작)로 잡았다. 코드에서 쓰이는 그룹과 겹치지 않는 것은 확인했으나, `COMCODE_TB` 에 실제로 비어 있는지 확인이 필요하다.

```bash
mysql -h 172.22.0.40 -u erp_user -p erp -e "SELECT TYPE_CD, TYPE_NAME FROM COMCODE_TB WHERE TOP_CD = '00' ORDER BY DIS_ORDR;"
```

### ③ 외출 기간을 날짜로 셀지 시각으로 셀지

`OUT_DAYS` 를 정수 일로 잡았다. 같은 날 나갔다 들어오면 0일이 된다. 반출대기가 일 단위 지표라 문제는 없어 보이지만, 분 단위로 눌러야 한다면 `OUT_MINUTES` 로 바꾸는 편이 낫다.

### ④ 상태를 바꾸는 API 를 어디에 둘지

지금 `/sam/loc/scan.do` 하나가 위치만 기록한다. 보관 · 꺼내기 · 외출 · 복귀 · 반출 · 폐기 · 확인 · 사진을 각각 엔드포인트로 둘지, `/sam/sst/change.do` 하나에 동작 코드를 받을지 정해야 한다. 폰 화면 설계와 같이 봐야 한다.
